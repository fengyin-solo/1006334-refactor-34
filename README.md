# 城市地下综合管廊运行维护管理平台

面向管廊主体台账、入廊管线登记、廊内环境监测、通风排水消防、结构沉降与渗漏处置、巡检检修与隐患整改、入廊作业审批和运维值班的一体化城市地下综合管廊运行维护管理工作台。

这是一个**纯前端**管理平台：Vue 3 + Vite + TypeScript，仓库里没有后端服务。业务数据由
`frontend/src/data/` 下的本地数据层提供：首次打开用示例数据播种，之后的登记、筛选与状态流转
结果都持久化在浏览器 `localStorage` 里，刷新或重开浏览器都还在。dev server 已关掉自动打开页面，
启动后按终端打印的地址手工打开。

## 目录结构

```text
.
├── frontend/                 Vue 3 + Vite + TypeScript 前端（唯一运行单元）
│   ├── src/views/            每个业务模块一个页面
│   ├── src/api/local-service.ts   本地数据服务：列表、筛选、动作流转、导出
│   ├── src/data/             模块元数据 / 示例数据 / localStorage 持久化
│   ├── src/stores/           会话与筛选状态
│   └── vite.config.ts        dev server 配置（open: false，无 /api 代理）
├── .gitignore
└── docker-compose.yml
```

## 启动

```bash
cd frontend
npm install
npm run dev
```

前端默认监听 `http://127.0.0.1:5173/`，dev server 不会自动打开浏览器，需要自己访问。

生产构建：

```bash
cd frontend
npm run build
```

## 约定

- 每个模块的页面在 `frontend/src/views/<模块>/index.vue`，页面只负责渲染，读写统一走
  `frontend/src/api/local-service.ts`。
- 字段、状态、动作与流转目标集中在 `frontend/src/data/modules.ts`；示例数据在
  `frontend/src/data/seed.ts`。
- 状态流转只允许在 `local-service.ts` 里改，页面组件不做业务判断。
- 想回到初始数据：清掉浏览器里 `urban-utility-tunnel:entries` 这一项，或调用 `resetModule(模块)`。

## 入廊作业审批：一份判定，各处共用

历史上跳转判定散在四处（列表按审批状态算一遍、确认批准/驳回动作里各算一遍、导出又算一遍），
规则还不一致（同一份申请列表里是已驳回、导出后成了已完工）。现已收拢为
`frontend/src/domain/entry-approval.ts`（审批域引擎）这一份实现：

- **校验只一处**：申请编号（`ENTR-XXXX`）、申请单位、作业舱室、安全措施同校于 `validateDraft`；
  安全措施为空不进入审批队列，按**待补材料**处理并给出说明，补齐后凭同一编号回到待审批。
- **推进关系只一份**（`TRANSITIONS`）：

  ```text
  待补材料 --补齐材料--> 待审批        待补材料 --驳回申请--> 已驳回
  待审批   --确认批准--> 已批准        待审批   --驳回申请--> 已驳回
  已批准   --确认完工--> 已完工        已驳回 / 已完工为终态
  ```

  列表可执行动作（`availableActions`）、`runAction`、导出状态（`projectEntry`）、
  待办口径（`isPendingStatus`）、异常口径（`isAbnormalStatus`）全部取自这里，页面不再另写。
- **导出列与字段不变**：仍是「编号 + 8 个登记字段 + 当前状态」，只是「当前状态」改取引擎判定，
  列表与导出永远一致。
- **重复提交去重**：同一申请编号不产生第二条；待补材料件补齐材料后并入原条。
- **同一动作连点幂等**：头一回推进并落台账，后续几回只往该台账条目的轨迹追加
  （`events[].repeat`），账上始终一条。
- **审批结论落维保台账**：批准→`检修中`、完工→同一条更新为`已完工`、驳回→同一条留`待开工`
  并注明缘由；联批条目检修编号为 `MNT-申请序号`，台账侧只读，冲突一律以审批域为准。
  申请与台账在 `saveAll` 一次本地事务里同落，待办清单与台账同源读数（`todoSummary`），
  差异可在页面一键「对账补登」（`reconcileTodo`）。
- **归属控制**：入廊作业审批由责任班组「廊内运维一班」归口；非责任班组（外单位、其他班组）
  入口只读，提交与越权改动在引擎 `authorize` 按归属驳回（页面置灰只是体验，服务层仍强制）。
  页面顶部可切换演示身份。

### 存量回填（一次性、版本化）

`frontend/src/domain/migration.ts` 在新代码首次读到旧数据时执行一次（版本号
`urban-utility-tunnel:migration-version`，只补不删、幂等可重入）：

- **历史审批记录不改写**：四个正式状态的结论原样保留；非正规历史记法也不改存储值，
  仅在读时归一到待审批（申请确在途、保守回队列），所以「在途申请仍按原结论走」。
- **提交日期按登记时刻回填**：存量无此字段，以 id 顺序对基准日 2026-09-01 逐日递增。
- **审批人员值班岗位推定**：早年纸质审批未录入、具体人名不可考，不杜撰责任人，按提交日期
  星期取岗位并落「岗位（推定）」，轨迹注明缘由，真人记录优先且可随时覆盖：

  | 提交日（星期） | 推定岗位 |
  | --- | --- |
  | 周一 / 三 / 五 | 白班值班长（巡检任务重的奇数工作日） |
  | 周二 / 四 / 六 | 夜班值班员 |
  | 周日（仅应急值守） | 值班主管 |

- **存量台账按登记时刻落库**：已批准/完工/驳回的申请按结论补登联批台账；早期条目缺项
  （更换部件、完工日期等）一律空着，在内部「台账说明」注明「缺项空着，未杜撰补录」。
  所有回填动作都留一条 `存量回填` 轨迹事件（内部字段，不进导出）。

### 两条路径的先后与冲突兜底

审批流与台账流是同一份数据的两个面，先后定为「**先落审批结论、再同步维保台账**」，
两步在一次 `saveAll` 内提交，任一不满足整组不写；冲突时台账侧联批条目只读、
通用检修动作拒绝，以审批域为权威（台账是审批的投影），已悬挂的台账（申请侧已不存在）
保留留存、只报差异不自动删除——台账是合规记录，不能随申请清理而消失。

### 内部字段

下划线开头的 `_提交日期 / _归属班组 / _来源申请编号 / _缺项缘由 / _台账说明` 与
`events` 轨迹只用于内部判定与留痕，不出现在表格列和导出 CSV 中。
